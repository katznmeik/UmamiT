# Motion review: v0.6.1 (taste per infusion, folding GESCHMACK, photo viewer, catalog kind groups, Design)

Read-only review of `git diff 28083ba0...74c67735` (`feature/journal`, `feature/brew`, `feature/catalog`,
`feature/settings`, `core/ui`, `core/designsystem`, `app`) against `docs/specs/03-ux-ui.md` §3.6 (tokens in
`UmamiMotion`, D-041 calm and functional, D-055 reduce motion), the v0.6.1 blocks of SCR-05, SCR-16, SCR-19, SCR-25
and SCR-28, D-114 and its build notes, and the `/review-animations` standards translated to Compose (the skill cannot
run in a subagent; same form as `v0.6.0-motion-review.md`): spatial consistency, interruptible springs for
user-driven changes, draw-phase opacity and no per-frame recomposition, reduce motion, exits faster than entries.

**Rule 8 first.** Nothing proposed here touches the alert path. The only `feature:brew` file in scope is
`TimerTaste.kt`: the button is hidden in the composition that decides the alert (`graphicsLayer { alpha = if (shown)
faded else 0f }`, `animationSpec = snap()` when it hides), the sheet is not composed on the alert surface (no exit
animation, keyboard hidden on dispose), `alertEnter` stays `snap()`. M13 to M15 record that and propose no change; the
one proposal on that file (M7) only swaps a reduce-motion branch for the `fade` token on the *appearing* path
(never into ALERTING) and leaves `shown`, the `snap()` on hiding and the sheet host as they are.

PO rule kept from v0.6.0: every tasting input is optional, so no motion marks an empty input. Checked: the new
chip row, dots, *Anpassen*, note field and the timer's button have no pulse, shake, highlight or auto-focus.

Fix: 5, optional: 3, leave: 13. Sections 2 and 3 hold the answers to the PO questions.

Tokens used are all from `UmamiMotion`; the diff has no hand-written easing. The v0.6.0 findings are closed in this
diff: the radar eases in (v0.6.0 M1, `SessionTasteSection.kt:328`) and the hero glide takes `motion.sheet()` (M4,
`PhotoHero.kt:74`).

## 2. Reduce motion, in one place

- **On the device** (animator scale 0): every spring, tween and fade here ends on its first frame; the fold, the radar,
  the chip change, the chevrons, the viewer's fade, the double-tap zoom and the catalog row travel are instant. Nothing
  in the diff needs a branch for it.
- **In-app path** (`reduceMotion = true` at scale 1, as tests force): springs and `standard()` snap, fades shrink to
  100 ms (`fade`, `exitFade`). The only place that deviates from the token is M7; it changes nothing on the device.
- The viewer's double-tap under M3 uses `sheet()`: it snaps there, as it should; pinch is direct manipulation and is
  never animated.

## 3. Questions for the PO

1. **Position of *Anpassen* (M6).** Unfolding GESCHMACK makes the toggle you just tapped slide up by the height of the
   one-line summary and the note line, while the sliders open below it. Keep that (no change), or move the toggle
   to a fixed place above the radar or summary line? This changes the SCR-16 layout, so it goes through the process
   (grilling, spec, ticket).
2. **Chip row when you clear a kind chip (M8).** The row glides back to its start (as specified), so the chip you just
   tapped slides out from under your finger. Keep, or leave the row where it is when the clear comes from the row's
   own chip, and scroll to the start only after *Zurücksetzen*, „Filter zurücksetzen" and *Alle zeigen*?
3. **Theme switch (M21).** A pick changes the colours at once, then the system re-creates the app a moment later, and
   the open *Design* dialog shows again. Accept that, or apply the system night mode only on *Fertig* (so the
   dialog is gone and the two steps become one)? The second changes SET-05 („a pick applies at once").

## 4. The PO's answers (2026-11-12, as options)

1. Q1 / M6: keep as built.
2. Q2 / M8: keep as specified.
3. Q3 / M21: apply the system night mode when the *Design* dialog closes, not on each pick (03 SCR-25 and D-114 amended). Goes into the fix round.
