## Checked and left out

- **`runsWithService`** (`core/timer/.../notification/LiveUpdateProgress.kt:8`) repeats the engine's `needsService` (`core/timer-engine/.../ForegroundService.kt:17`) on the UI state. The notification code has only the UI state, so removing the copy means a new field on `TimerUiState.Active` that every fake and test state must set. `ForegroundServiceContractTest` and the engine's invariant test check the two against each other. Left as is.
- **`TimerUiState.Active.inSlot`** (`TimerUiState.kt:95`, `:102`, `:223`): a nullable slot with a fallback and a normalisation, where a `slot` field with a default would do. It would rename a constructor argument in 13 test places for five lines. Style-level.
- **`BrewSessionController.send(event)`** (`BrewSessionController.kt:763`, „to the front slot"): no caller in the app, but about 190 in 26 test files of three source sets. It cannot move to one test helper they all see. Kept.
- **The `slot = TimerSlot.BREW` defaults** of `ScheduledTime`, `EventHandled`, `AlarmReceived`, `Recovered`, `FireTime` and of `TimerActionReceiver.intent` / `requestCodeOf`: the app always passes the slot; the defaults serve tests written before two brews. Removing them edits many tests for no line saved.
- **`BrewSessionController.kt`** (764 lines, evidence §4 #4): 402 of them are code. `ProcessRecovery` and `SideBySide` are inner classes because they run inside the controller's turn (`handle`, `slots`, `clocks`); moving them out needs a back-reference, which is a change of structure on the recovery path, not a move of lines. No finding.
- **`AndroidAlertOutputs.kt`** (453 lines, #23): seven small classes in one file. One file per class would be pure moves like DAT-A-14, on the alert path and with no line saved. Not proposed.
- **The two re-post mechanisms** (`BrewTimerService.kt:170–186`, `TimerNotifications.kt:150–164`): the same idea, but one is guarded by the service's foreground id and the other by a map per notification id; merging them would change which post wins.

The numbers identify pending intents that survive an app update (`PendingIntentCodesTest`, `UpdateFromV022Test`, `UpdateFromV041Test`); out by risk.
