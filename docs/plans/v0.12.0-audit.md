### Findings

#### A-01 — Start (SCR-02): *Aufguss starten* overlaps the header picture (PO point, D-138 Q11, item 18)
- **Problem:** the picture and the card sit apart (the band's 8 dp bottom padding, then the card), so they read as two things and the block takes 256 dp under the title bar before *Zuletzt aufgegossen*.
- **Proposal:** the picture keeps its 120 dp band; the first card of the block (*Aufguss starten*, or *Aufguss fortsetzen* in the active state, with the cards below it) is pulled up so it overlaps the picture's visible lower edge, and everything below moves up by the same amount (a layout modifier that places the card column at −(8 + overlap) dp and reports its height shorter by as much; drawn after the picture, so on top). Two values to pick from, fixed dp (not scaled with font, so the picture stays visible at font 2.0):
  - **variant a:** overlap **24 dp** ≈ one third of the card's 72 dp → the block moves up 32 dp;
  - **variant b:** overlap **36 dp** ≈ one half → the block moves up 44 dp; the card then covers the lower blossoms.
  - Net effect with A-02's taller card (72 dp instead of the 48 dp text button, plus the 12 dp gap): *Zuletzt aufgegossen* starts 12 dp higher than today in a, 24 dp higher in b (at font 1.0, light).
  - **Gap between the cards: 12 dp** (`UmamiSpacing.Small`), the gap *Aufguss fortsetzen* → *Aufguss starten* already uses; the same 12 dp to the *Schnelltimer* card (A-02). The section header below keeps its 24 dp top padding. Reliability banner stays above the picture, the nudge card below the cards (item 18). Empty state: no picture, so no overlap (A-02 picture). No shadow (flat design, 03 §3.3).
- **Kind:** component/layout
- **Pictures:** A-01_before.png / A-01a_after.png / A-01b_after.png; `_font2` and `_dark` of each (A-01_before_font2.png, A-01a_after_font2.png, A-01b_after_font2.png, A-01_before_dark.png, A-01a_after_dark.png, A-01b_after_dark.png); active session, variant a: A-01a_active_before.png / A-01a_active_after.png. **All after pictures already contain the A-02 card**: the PO judges the block as a whole.

### Findings

#### A-20 — „Gespeichert" sheet (SCR-06): unrated stars you can barely see
- **Problem:** the empty stars are `outlineVariant` at 45 % alpha, which is ≈ 1.2:1 against the sheet in both themes (measured #E0E1D8 on #F7F5F0; #313830 on #232B24). The two rating rows, the sheet's main input, read as faint ghosts that are easy to miss, and they fall well below the 3:1 that a control's graphic needs (WCAG 1.4.11).
- **Proposal:** draw an unrated star (and the unfilled half of a half star) as an **outline** in `onSurfaceVariant`: 4.99:1 light, 6.1:1 dark. Filled stars stay `primary`, so the state shows in shape as well as colour. The outline is the existing star path of `ic_star_filled` stroked at about 1.4 dp, round joins, as a new `ic_star_outline` vector (in the render: stroke 44 of the 960 viewport). It is drawn only while the star is not full, so a full star has no grey rim. Size (30 dp), 48 dp targets, the tap cycle, haptics and TalkBack are unchanged. No new colour token.
- **Kind:** type/colour
- **Pictures:** A-20_before.png / A-20_after.png; A-20_before_dark.png / A-20_after_dark.png. The diff is confined to the two star rows. No golden of the sheet has a rated star, so the half-star look is not rendered.
- **Modules/files:** `core/ui/.../RatingStars.kt` (`Star`, `EMPTY_ALPHA` goes), `core/designsystem/.../icon/UmamiIcons.kt` + `res/drawable/ic_star_outline.xml`  **Tier:** T2  **Timer code:** no

### Findings

#### A-40 — Meine Tees (SCR-08) and Katalog (SCR-19): the filter row fades at the edge
- **Problem:** The sideways-scrolling chip row cuts a pill hard at the screen edge (*Kategorie* on Meine Tees, the next kind on Katalog). On Katalog it also cuts *Filter* on the left when a selected kind is revealed (`Catalog_listBlack`).
- **Proposal:** Keep the row's scroll. On each side that has more content, the row fades to transparent over 24 dp at the screen edge, so it fades into whatever background is behind it. The fade is an alpha mask (offscreen layer plus a `DstIn` gradient), and there is no fade on a side where nothing is cut. It is static, with no timed animation. The fade strength follows the scroll offset over the first and last 24 dp, so it thins out as the row reaches either end. Scrolled to its end, the last pill keeps the 20 dp side margin (the row's inner padding, unchanged). Implementation is one shared modifier, `Modifier.horizontalEdgeFade(scrollState, width = 24.dp)`, in `core:ui`, put before `horizontalScroll` on both rows.
- **Kind:** component/layout
- **Pictures:** A-40_before.png / A-40_after.png (+ _font2, _dark); A-40_katalog_before.png / A-40_katalog_after.png (+ _font2, _dark); A-40_end_after.png (Meine Tees scrolled to the end: the left side fades, and *Archiviert* sits 20 dp from the edge with no fade on the right).
- **Modules/files:** core/ui (new `EdgeFade.kt`), feature/collection `MyTeasParts.kt` (`MyTeasChips`), feature/catalog `CatalogFinding.kt` (`CatalogFilterChips`). Re-recording the Collection_* and Catalog_* goldens with a chip row is a mechanical follow-up. The `Catalog_chipRow` golden (2400 dp wide, nothing cut) shows no fade.  **Tier:** T2  **Timer code:** no
- **Depends on / conflicts with:** — (the same modifier fits any other chip row in the app, e.g. the SCR-16 infusion chips)
