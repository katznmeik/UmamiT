# v0.7.2 restructuring design (#304): D-121 – D-127

The design of the seven restructurings the PO picked in the triage (#303). Docs only. Read against `main`-equal
sources at `bce78141` (2026-11-16); line numbers are from that commit and move once #305 and #306 are in, so every
implementer takes them again. The steps are in #307 (D-121 – D-125) and #308 (D-126, D-127).

**Approved by the PO on 2026-11-16** (eight questions as options; recorded in each decision): variant A of every
design below, and for all seven that 06 stays unchanged, every step is T3, and the order at the end of this file.
The variants not taken are kept in one line each.

## For all seven

- **06 §3 and `build-logic`'s module rules, before and after: unchanged.** No module is added, no module edge is
  added or removed, no pure module is touched. `ModuleRules` checks project and Android dependencies at
  configuration time (`enforcePure`, `enforceFeature`); no step adds a project dependency. Two build files change
  (`core/ui`, D-123; `core/timer`, D-127), neither with a project dependency.
- **`06-architecture.md`: no section changes.** §3's tree names modules, not files; §5.3 names no file of the
  refresh; §7 names the gates, not Detekt's source folders. Checked by grep for every type and file below.
- **Proof (plan „Proof"):** no golden, no schema, no DataStore key, no user-visible string, no motion value changes
  in any step. A step that turns out to need one is stopped and answered in its ticket.
- **Tiers:** every step is **T3** (Opus `medium`), as #307 and #308 say; in #308 a failure escalates to T4.
- **Per step:** the orchestrator reads the diff, runs the step's scoped check, then the plan's cross-module check,
  pushes, and checks CI before the next step builds on it.

**Risk.** Goldens, keys, timer path: none. Schema: none (`toEntity` fills the same columns; `CatalogContentHash`

## D-123: helpers and `PastDatePickerDialog` in `core:ui` (CAT-A-08 + UI-A-04) → #307

**Target (public in `core:ui`, package `com.umamit.core.ui`):**
- `PastDatePickerDialog(initial: LocalDate?, latest: LocalDate?, confirmLabel: String, cancelLabel: String,
  onPick: (LocalDate) -> Unit, onDismiss: () -> Unit)` in `PastDatePickerDialog.kt`. `latest == null`: no limit
  (`DateField`). Confirm calls `onPick` then `onDismiss`. The UTC-midnight conversion becomes private to this
  file; no feature keeps a copy.
- `teaTypePlaceholderColor(teaType: String?): Color` (`@Composable`), the shared body of the catalog's and
  *Meine Tees*' `placeholderColor`. The new name keeps it apart from the Journal's `placeholderColor`, which is a
  different rule and stays.
- `Context.openInBrowser(url: String, @StringRes noBrowserMessage: Int)`.

**The initial day.** `DateField` and the session editor clamp it to *latest*; the catalog sheet does not.
`AddSheetState.pickDate` keeps `date ≤ today` (`minOf(day, today)`, and it starts at `today`), so clamping there
changes nothing. **PO: variant A**, the dialog always clamps, no flag. Not taken: B, a `clampInitial` parameter
the catalog sheet sets to `false`.

**Build.** `core/ui/build.gradle.kts` gains `implementation(libs.androidx.core.ktx)` for `toUri` (already in the
version catalog and the app). No project dependency: every feature has `core:ui` through the feature convention
plugin; `core:ui` already has `core:designsystem` for the colours.

**Steps.**
1. `teaTypePlaceholderColor` and `openInBrowser` into `core:ui`; `feature:catalog` and `feature:collection` use
   them; their strings stay their own.
2. `PastDatePickerDialog` into `core:ui`; `CatalogAddSheet`, `DateField` (inside its `AlertGated`),
   `SessionDateDialog` use it; labels stay each feature's strings.

Check per step: the three features' unit tests and `verifyRoborazziDebug` for them (`CatalogAddSheetTest`,
`TeaEditorScreensTest`, `SessionEditorScreenTest`, the catalog and *Meine Tees* list goldens).

**Risk.** Goldens: the same composables with the same values, proved by `verifyRoborazziDebug`. Strings: none
added or removed. Schema, keys, timer path: none (`feature:brew` is not touched).

## D-125: settings routes once, `isOnTop` (UI-A-01 + UI-A-10) → #307

**Found.** The two registrations differ in more than how they navigate:

| | Root graph (above the timer) | A tab's graph |
|---|---|---|
| Settings route | `TimerSettingsRoute` | `SettingsRoute` |
| Navigation | `navigateAbove(route) { … }` (records the alert) | `navController.navigate(route)` |
| A vessel | not gated, `launchSingleTop` | `resumedOnly`, no `launchSingleTop` |
| *Neues Gefäß* | `dropUnlessResumed`, `launchSingleTop` | `dropUnlessResumed` |
| Scroll-to-top request | none | the tab's |
| „Erneut einrichten" | the root's `rerunSetup` | `settings.onRerunSetup` |
| Order registered | settings, teaware, vessel, about, diagnostics | settings, about, diagnostics, teaware, vessel |

None of this may change, so the function takes each graph's own lambdas instead of one `navigate`.

**Target (`app`, new file `SettingsRoutes.kt`; `internal`):**
- `class SettingsNav(back, open: (route: Any) -> Unit, openVessel: (id: String) -> Unit, addVessel: () -> Unit,
  closeVesselEditor: (savedId: String?, archived: ArchivedVessel?) -> Unit, alertKey: String?,
  scrollToTopRequest: Int = 0, rerunSetup: () -> Unit)`, built once per graph with today's lambdas.
- **PO: variant A.** `inline fun <reified S : Any> NavGraphBuilder.settingsRoutes(settings: SettingsScreens,
  nav: SettingsNav)` registers all five; the root calls it with `TimerSettingsRoute`, a tab with
  `SettingsRoute`. Not taken: B, only the four destinations with the same route.
- `NavHostController.isOnTop(entry)` and `popIfOnTop(entry)` in `Routes.kt`'s neighbour `NavOnTop.kt`; the eight
  sites use them (`UmamitApp.kt:657, :674, :710, :740, :762`; `UmamitRoot.kt:672, :682, :710`).
  `UmamitApp.kt:588` reads the top entry for another purpose and stays.

The order in which a graph registers its destinations has no effect on navigation (no deep links, typed routes);
one graph's order changes in the source.

**Steps.**
1. `isOnTop` / `popIfOnTop` and the eight sites. Check: `ShellNavigationTest`, `TeaEditorFlowTest`,
   `RecipeEditorFlowTest`, `SessionPageFlowTest`, `SetupLinksFlowTest`.
2. `SettingsNav` and `settingsRoutes`; the tab's graph uses it. Check: `ShellNavigationTest`,
   `TeawareNavigationTest`, `ThemeModeFlowTest`, `UnreadableSettingsStartTest`.
3. The root graph uses it. Check: the same and `TimerNavigationTest`, `TwoTimersNavigationTest` (a route above
   the timer gives way to a new alert, rule 8).

Then `:app:testDebugUnitTest` and `verifyRoborazziDebug` (`ShellScreenshotTest`).

**Risk.** Navigation, medium: the root's `navigateAbove` is what lets a new alert close these routes (rule 8);
step 3 is on its own for that. No fenced file is touched (`UmamitRoot.kt` and `UmamitApp.kt` are not on the
fence list of `v0.7.2-audit-timer.md`). Goldens, schema, keys: none.
