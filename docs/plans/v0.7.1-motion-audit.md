## 1. The unlock cause: „old content, then a jump" (Q14)

**Cause.** After unlock the first frame is composed from values captured before
the screen went off, and they are corrected only one tick (up to 1 s) or one
upstream restart later. Two code paths do this, and both show on the shell's
most-seen surfaces (the active brew bar, Start's *Aufguss fortsetzen* card, the
timer screen):

1. **The second tickers stand still while the phone sleeps.** Each ticker samples
   the clock, then `delay`s to the next second boundary:
   - `rememberTimerNow`: `feature/brew/.../timer/TimerScreen.kt:191-200`. The
     timer screen's digits, caption and pre-alert; also the other timer's row,
     `TimerOtherRow.kt:82`.
   - `displayTicks`: `feature/brew/.../timer/ActiveBrewMapping.kt:48-56`. The
     bar's digits and mini ring, through `TimerAppWiring.kt:122`.
   - `rememberTickingNow`: `feature/home/.../HomeScreen.kt:254-266`. Start's
     active card.

   `delay` counts uptime (`Handler.postDelayed` / `System.nanoTime`, both
   without deep sleep), while `now` is `elapsedRealtime` (with deep sleep). With
   the screen off and the CPU suspended between the timer's exact alarms, the
   pending `delay` does not run out. After unlock the composition still holds
   the `now` sampled before sleep. The digits show the lock-time value until the
   rest of that `delay` has passed (≤ 1 s of awake time), then they jump by the
   whole sleep. On the timer screen the frame-driven ring reads
   `nowElapsedMs()` while drawing (`TimerScreenParts.kt:300-312`), so ring and
   digits disagree in that window. Nothing re-samples on `ON_START`.
2. **The active brew bar replays its cached value.** `TimerActiveBrewSource`
   (`app/.../timer/TimerAppWiring.kt:106-131`, also `barSlots` at 110-113) is
   `stateIn(lifecycleScope, WhileSubscribed(5 000), <first value>)`.
   `collectAsStateWithLifecycle` (`UmamitApp.kt:208-210`) stops collecting at
   `ON_STOP`. After 5 s the upstream (`combine` → `flatMapLatest` →
   `displayTicks`) is cancelled, and the StateFlow keeps its last value: the bar
   (digits and the `level` float state of the mini ring) as it was at lock time.
   At `ON_START` the collector gets that stale value first. The restarted
   upstream gets through `combine`'s and `flatMapLatest`'s channel hops only a
   dispatch later, so the first frame can draw the stale bar before the fresh one
   replaces it. If the brew ended or changed slot meanwhile, the bar then also
   shrinks or grows with its spring, and the content above it glides by 72 dp.
   The synchronous first value (line 130) is computed only once, when the
   activity is created.

The **same path** is behind the timer → shell exit (group 4, A-02). While the
timer is on top the shell is not composed (Navigation keeps only the top entry).
The bar's flows go stale after 5 s, and the shell that comes back draws the bar
of the moment the timer opened.

A return from recents adds the system's task snapshot (the last frame before
leaving) until the app's first frame. Whatever differs in that first frame reads
as a jump, so the first frame has to be fresh (A-01, A-02).

**Fix direction (Q19, „hold, then show fresh"):** re-sample at `ON_START`, which
runs before the first frame after unlock. Then the first frame is already fresh,
and nothing has to be held for these surfaces (A-01, A-02). Lists that need a
read (the Journal) hold their last frame for at most 150 ms and cross-fade with
`fade` if the content changed (A-09).

## 3. Findings

### A-01: second tickers frozen in deep sleep (group 1, HIGH)

- **Place:** `feature/brew/src/main/kotlin/com/umamit/feature/brew/timer/TimerScreen.kt:191-200`
  (`rememberTimerNow`; used at :103 and in `TimerOtherRow.kt:82`);
  `feature/brew/.../timer/ActiveBrewMapping.kt:48-56` (`displayTicks`);
  `feature/home/src/main/kotlin/com/umamit/feature/home/HomeScreen.kt:254-266`
  (`rememberTickingNow`).
- **Symptom:** after unlock (or turning the screen on over the timer), the
  digits on the timer, the bar and Start's card show the time from before the
  screen went off for up to 1 s, then jump. On the timer the ring is already
  right and disagrees with the digits.
- **Cause:** see §1 (1). `delay` runs on uptime, `now` is `elapsedRealtime`,
  and nothing re-samples on `ON_START`.
- **Fix (Compose):** re-sample at `ON_START` and restart the loop.
  ```kotlin
  @Composable
  internal fun rememberTimerNow(state: TimerUiState.Active, nowElapsedMs: () -> Long): State<Long> {
      val now = remember(state, nowElapsedMs) { mutableLongStateOf(nowElapsedMs()) }
      var starts by remember { mutableIntStateOf(0) }
      // ON_START runs before the first frame after unlock: the first frame is fresh (D-117 Q19).
      LifecycleStartEffect(state, nowElapsedMs) {
          now.longValue = nowElapsedMs()
          starts++
          onStopOrDispose {}
      }
      LaunchedEffect(now, nowElapsedMs, starts) {
          while (true) {
              val delayMs = state.nextTickDelayMs(now.longValue) ?: break
              delay(delayMs)
              now.longValue = nowElapsedMs()
          }
      }
      return now
  }
  ```
  Do the same in `HomeScreen.rememberTickingNow`. `displayTicks` restarts with
  A-02's lifecycle-driven source, because it emits `nowElapsedMs()` first.
  **Test:** a fake clock that advances `elapsedMs` without advancing the test
  dispatcher (a sleep), then `ON_START`: the next frame shows the new second.
  The 04 §12 timer tests must pass (rule 8). The alert is not affected: ALERTING
  comes from the controller's state, not from this ticker, and `alertEnter`
  stays `snap()`.
- **Decision:** direct fix (removes a stale frame; no token or behaviour
  change). **Timer path:** yes (`feature:brew`; also `feature:home`).

### A-02: the active brew bar replays a stale cached value (groups 1 and 4, HIGH)

- **Place:** `app/src/main/kotlin/com/umamit/app/timer/TimerAppWiring.kt:106-131`
  (`activeBrew`, `alongside`, `barSlots` with `SharingStarted.WhileSubscribed(5_000)`);
  read at `UmamitApp.kt:208-210`.
- **Symptom:** (a) after unlock the bar shows the lock-time digits and mini-ring
  level, then jumps. If the brew ended meanwhile, the bar also shrinks away and
  the content glides 72 dp *after* the screen is already back. (b) Timer →
  shell: the shell that comes back draws the bar from when the timer opened,
  then corrects it. After *Sitzung beenden* the just-ended brew's bar can
  appear, then shrink away.
- **Cause:** see §1 (2). The StateFlow keeps the value it had when the last
  collector left; its synchronous first value is computed once, when the
  activity is created.
- **Fix (Compose/Flow):** drive the bar by the activity's lifecycle instead of
  by subscribers, so it is fresh whenever the activity is started, also while
  the shell is not composed:
  ```kotlin
  private val bars = MutableStateFlow(snapshot())            // Bars(activeBrew, alongside, slots)
  init {
      scope.launch {
          lifecycle.repeatOnLifecycle(Lifecycle.State.STARTED) {
              bars.value = snapshot()                          // in ON_START, before the first frame
              combine(slots) { it.toList() }.distinctUntilChanged()
                  .flatMapLatest { states -> ticksFor(states) } // displayTicks per active timer
                  .collect { bars.value = it }
          }
      }
  }
  override val activeBrew = bars.map { it.first }.stateIn(scope, Eagerly, bars.value.first)
  ```
  `snapshot()` is today's synchronous first value, `pick(activeNow())?.let {
  brewAt(it, clock.elapsedMs(), level) }`, for both halves and the slots. The
  constructor takes the activity's `lifecycle` (it already takes
  `lifecycleScope`). While the timer is on top, the source still ticks once per
  second, which is negligible. Keep the ALERTING bar's snap to static matcha
  (03 §3.8): the snapshot carries the alerting state in frame 1.
  **Test:** `TimerAppWiringTest` with a lifecycle moved STARTED → CREATED, then
  the clock advanced 10 s, then STARTED again: `activeBrew.value` is fresh
  synchronously after `ON_START`. Also a re-composed shell after a finished
  session reads `null` in its first frame.
- **Decision:** direct fix. **Timer path:** no (`app`; it reads the
  controller's state, and the controller and engine are unchanged).

### A-03: Start arrives in pieces on a cold start (group 1, MEDIUM)

- **Place:** `feature/home/.../HomeViewModel.kt:142-186` (initial `HomeUiState()`
  with `loading = true`; the low-stock card combined with
  `.onStart { emit(null) }` at :179); `HomeScreen.kt:98-121` (card slot above
  `Lists`), `:147` (*Aufguss starten* only when `!loading`).
- **Symptom:** after a cold start or process death the Start frame first shows
  the header and *Schnelltimer*. Then *Aufguss starten* appears above
  *Schnelltimer* and pushes it down. Then the low-stock card appears and pushes
  *Zuletzt* and *Favoriten* down.
- **Cause:** three emissions of partial state; each changes the layout.
- **Fix:** one ready state, held for at most 150 ms (Q19). Replace
  `.onStart { emit(null) }` with a first value that waits for the card, at most
  150 ms: `lowStock.observeCard().timeoutFirst(150.milliseconds, fallback =
  null)`, a small helper that emits `null` only if nothing came within 150 ms.
  The VM's state emits `loading = false` only together with that first card
  value. In `HomeScreen`, while `loading`, draw nothing below the header. When
  `loading` turns false, fade the body in with `fadeIn(motion.fade())`, without
  a slide. A card that arrives after the 150 ms still pushes the lists, which is
  acceptable and rare. **Rule 8:** the alert never waits for this. Start's
  question dialog is closed by the VM's own alert collector (`init`, :188 ff.),
  and the timer is brought to the top by the root, not by Start's state.
- **Decision:** direct fix (applies 03 §3.6 „no layout moves when data
  arrives"). **Timer path:** no.

### A-04: cold start shows the wrong window colour, then an empty frame (group 1, MEDIUM)

- **Place:** `app/src/main/res/values/themes.xml:4-7`
  (`android:Theme.DeviceDefault.DayNight`, no `windowBackground` and no
  `windowSplashScreenBackground`); `UmamitRoot.kt:181-184` (returns without
  content until `onboardingCompleted` is read); `MainActivity.kt:168-174`
  (`WindowBackground` sets washi only from the first composition).
- **Symptom:** the system splash and the first frames use One UI's default
  window colour (not washi `#F3F0E9`, not the dark `#1C231D`). Then comes a
  plain washi frame, then the app.
- **Cause:** the window theme predates the Compose theme („the Compose theme
  follows in M1-04"), and the root draws nothing while the settings are read.
- **Fix:** (1) the window theme takes the app's backgrounds:
  `android:windowBackground` and `android:windowSplashScreenBackground` =
  `#F3F0E9` in `values/`, `#1C231D` in a new `values-night/`, and the same for
  the navigation and status bar scrims if they show. The handed-over night mode
  (D-114) already makes `values-night` follow *Design*. (2) Hold the first draw
  while the root has nothing to show, at most 150 ms (Q19): a
  `ViewTreeObserver.OnPreDrawListener` on `android.R.id.content` that returns
  `false` while `onboardingCompleted.value == null`, and removes itself when
  the value is known or after 150 ms. Never hold when the start intent is
  `ACTION_OPEN_TIMER` or an alert plays (`alertKey.value != null`), so the
  full-screen intent's first frame is never delayed (rule 8, D-064).
- **Decision:** direct fix (03 §3.1 colours, no §3.6 value). **Timer path:**
  no (`app`), but the hold must skip the timer intent as stated.

### A-05: timer restored after process death draws nothing until recovery (group 1, MEDIUM)

- **Place:** `feature/brew/.../timer/TimerRoute.kt:66-81` (`null -> if
  (recovered) …`; nothing is drawn while `!recovered`).
- **Symptom:** back from recents after process death, with the timer on top:
  the root shows the window background (washi in the light theme), because the
  shell is not composed under the timer route. Then the dark timer appears.
  This is a light flash before a dark screen.
- **Cause:** the route's „no Active state" branch draws no surface. The
  timer's dark background belongs to `TimerScreen`, which is not composed yet.
- **Fix:** the route always draws the Steeping background under its content:
  ```kotlin
  Box(modifier.fillMaxSize().background(SteepingColorScheme.background)) {
      when (val active = view.shown) { null -> …; else -> TimerScreen(…) }
  }
  ```
  This matches `ShellCover` (`UmamitRoot.kt:786-791`). It draws no content and
  delays nothing (rule 8: recovery and the alert path are unchanged).
- **Decision:** direct fix. **Timer path:** yes (`feature:brew`).

### A-06: the Journal's cache dies with each activity re-creation (group 1, MEDIUM)

- **Place:** `feature/journal/.../JournalSources.kt:29` (plain `@Inject`
  constructor, no scope), `:54-57` (`lastSessions`, `lastList`); injected into
  the activity at `MainActivity.kt:70-71`.
- **Symptom:** after a re-creation (the *Design* hand-over, D-114; the phone's
  night-mode switch under *System*; a font-scale or locale change) the Journal
  tab's first frame has `list == null` (`JournalScreen.kt:107`: an empty body
  under the title). Then the list pops in. A cold start does the same on the
  Journal's first visit.
- **Cause:** each activity gets a new `JournalSources`, so the „last read" that
  JRN-09 relies on is gone.
- **Fix:** scope it to outlive the activity: `@ActivityRetainedScoped` on
  `JournalSources` (Hilt's activity-retained component survives configuration
  changes). `@Singleton` also works and keeps the list across a stopped
  activity. A cold start still has no cache: there the tab-switch delay (90 ms)
  and A-09's hold cover the first read.
- **Decision:** direct fix. **Timer path:** no.

### A-07: `alertKey` starts as `null` in a re-created activity (group 1, LOW)

- **Place:** `app/.../MainActivity.kt:110`:
  `brewTimer.state.map { it.alertKey() }.stateIn(lifecycleScope, Eagerly, null)`.
- **Symptom:** a re-creation during an alert (the D-114 window) composes its
  first frame as „no alert". The root's `instant()` checks
  (`UmamitRoot.kt:224`), the `SavedSheetHost` guard (`SavedSheet.kt:180`), every
  `AlertGate` and `SystemBarIcons` (`alerting = false`: light icons on the light
  alert surface) all see `null` for that frame.
- **Cause:** the seed is a constant, not the controller's current value. The
  bar does this right (`TimerAppWiring.kt:124-130`).
- **Fix:** seed with the current value: `stateIn(lifecycleScope, Eagerly,
  brewTimer.state.value.alertKey())`.
- **Decision:** direct fix (rule-8 hardening, no behaviour change). **Timer
  path:** no (`app`; `alertKey()` in `core:timer` is only read).

### A-08: the Design hand-over re-creates the activity (group 1, MEDIUM, to the PO)

- **Place:** `app/src/main/AndroidManifest.xml:46-49` (`MainActivity` without
  `android:configChanges="uiMode"`); `feature/settings/.../AppNightMode.kt:20-21,39-42`
  (`setApplicationNightMode`, „a change re-creates the activity"); PROJECT_STATE
  „Open from D-114".
- **Symptom:** closing the *Design* dialog with a new theme relaunches the
  activity: the window is replaced, every screen is re-composed, and Journal,
  bar and lists go through their first-frame paths (A-06, A-07). Under
  *System*, One UI's scheduled dark mode does the same while the app is open.
  An alert starting in that ≈ 0.5 s waits for the new window (D-114 note).
- **Cause:** a `uiMode` change is handled by a full relaunch.
- **Fix:** options in §4.1. Independent of the choice, A-06 and A-07 are
  needed.
- **Decision:** to the PO (changes D-114's mechanism: the theme switches in
  place instead of by re-creation). **Timer path:** no (but rule 8 adjacent).

### A-09: the Journal's earlier-list frame (group 2, HIGH)

- **Place:** `feature/journal/.../JournalRoute.kt:44-46`
  (`collectAsStateWithLifecycle(initialValue = sources.lastSessions)`), `:76-80`
  (`produceState(sources.lastList, sessions, today, locale)`).
- **Symptom:** a tab that comes back to the Journal draws the list of its last
  visit. If a session was saved meanwhile (the usual case: a brew just ended),
  the new day row and entry appear a frame or more later and push the list
  down, under the user's eyes. This is PROJECT_STATE's „Known from v0.6.0".
- **Cause:** `produceState` starts with `lastList`, then rebuilds twice: once
  from `lastSessions` (the same data, a wasted build on `Default`), and once
  when Room's fresh read arrives. On a large journal a build can outlast the
  tab switch's 90 ms out-phase, which until now hid the old frame.
- **Fix (Q19):** (1) skip the redundant build: in the producer, `if (read ===
  sources.lastSessions && sources.lastList?.builtFor == (today to locale))
  return@produceState`. (2) Hold, then show fresh: keep `lastList` only for the
  first 150 ms. If the fresh list arrives in that time and differs, swap it in
  place without animation. The tab is still invisible under `tabSwitch`'s
  90 ms delay, or the cross-fade has barely begun. If it arrives later and
  differs, cross-fade the list area once with `Crossfade(targetState =
  list.contentKey, animationSpec = motion.fade())`, where `contentKey` = the
  ids of the first visible days. A list that did not change is never faded.
  Keep `LazyListState` outside the crossfade, so the scroll position stays.
- **Decision:** direct fix (it implements the decided rule of 03 §3.6).
  **Timer path:** no.

### A-10: every tab switch composes the target tab from scratch (group 2, MEDIUM)

- **Place:** `app/.../UmamitApp.kt:216-282` (`rememberSaveableStateHolder` +
  `transition.AnimatedContent { tab -> … TabHost(…) }`).
- **Symptom:** the first frame of each tab switch (tens of times a day)
  composes a `NavHost`, the screen, a first `LazyColumn` layout and image
  requests for the incoming tab. At the same time the outgoing tab runs its
  90 ms fade. This is the most likely janky frame of group 2 under
  NFR-PERF-12 (≤ 1 frame over 16,7 ms, none over 50 ms).
- **Cause:** `AnimatedContent` disposes the old tab after the transition.
  Saved state survives (scroll, `rememberSaveable`), but composition and layout
  are redone each time.
- **Fix:** only if #285's baseline shows a tab switch over the limit. Keep
  visited tabs composed and switch them by graphics layer: a `Box` holding each
  visited tab in `key(tab)`. Hidden tabs get `Modifier.graphicsLayer { alpha =
  0f }`, are not placed for input (`Modifier.layout` that places them only
  while visible or transitioning), and are wrapped in
  `LocalLifecycleOwner`-scoped STARTED-capping, so their collectors pause. The
  alpha follows the same `tabSwitchOut`/`tabSwitchIn` specs through
  `transition.animateFloat`, so the tokens stay as they are. Predictive back's
  `seekTo` keeps working on the same `SeekableTransitionState`.
- **Decision:** direct fix (performance only, the tokens and the look are
  unchanged), conditional on the baseline. **Timer path:** no.

### A-11: popping recomposes the screen below in the pop's first frame (groups 2 and 4, MEDIUM, to the PO)

- **Place:** `app/.../UmamitApp.kt:629-637` (tab stacks: `popEnterTransition =
  None`, `exitTransition = KeepUntilTransitionsFinished`);
  `app/.../UmamitRoot.kt:277-306` (root: the same, the timer above the shell).
- **Symptom:** back from a detail recomposes the list below in the first frame
  of the pop. Timer → shell (back, or after *Sitzung beenden*) recomposes the
  **whole shell**: `UmamitApp`, four tab controllers, the selected tab's screen,
  the bar and the *Gespeichert* host. All of it lands on the first frame of the
  200 ms `exitFade`: a likely janky frame, and the frame that A-02's stale bar
  and A-15's empty frame make visible.
- **Cause:** Navigation Compose keeps only the top entry composed. Once the push
  has finished, the entry below has left composition (its state is saved and
  its ViewModels live). `popEnter = None` then needs it complete in frame 1.
- **Fix:** options in §4.2. Measure first: #285's timer → shell and detail →
  list transitions decide whether this is over budget.
- **Decision:** to the PO (option 2 changes the timer's navigation model, 03
  §2.2/§2.3 and the rule-8 machinery in `rememberTimerFirst`). **Timer path:**
  yes (the timer route and its exit).

### A-12: pushed screens show an empty Loading body, then the content pops in (groups 2 and 4, MEDIUM)

- **Place:** `feature/collection/.../detail/TeaDetailScreen.kt:131` (an opaque
  `background` box *without* the top bar); `feature/brew/.../setup/BrewSetupScreen.kt:120`;
  `feature/journal/.../session/SessionEditorScreen.kt:104`;
  `feature/collection/.../editor/TeaEditorScreen.kt:176`;
  `feature/collection/.../recipe/RecipeEditorScreen.kt:184`;
  `feature/teaware/.../VesselEditorScreen.kt:213`;
  `feature/teaware/.../TeawareScreen.kt:143`; `feature/stats/.../StatsScreen.kt:162`
  (first visit); `feature/collection/.../MyTeasScreen.kt:116` (cold start).
- **Symptom:** during the route's enter (`fade` 300 ms plus a 1/12 nudge with
  `standard`), the first frames show a top bar over an empty body. The tea
  detail shows an opaque empty sheet that covers the list, with no top bar.
  Then the content appears in one frame, part-way through the fade. Setup →
  timer starts with an empty setup above Start (the root's `fade`).
- **Cause:** each ViewModel is created with the entry and starts in `Loading`.
  The first Room read arrives a few frames into the enter, and the switch from
  `Loading` to data is not animated.
- **Fix:** (1) Loading draws nothing opaque: `TeaDetailUiState.Loading ->
  Unit` inside the scaffold, so the detail's top bar (title empty) shows like
  every other screen, never a bare background. (2) The content's first
  arrival fades in: wrap the body in `AnimatedContent(targetState = state is
  Loading, transitionSpec = { fadeIn(motion.fade()) togetherWith
  ExitTransition.None })`, or for screens with a single data state an
  `AnimatedVisibility(visible = state !is Loading, enter =
  fadeIn(motion.fade()), exit = ExitTransition.None)`. Nothing moves, and the
  existing tokens are used. A read that comes within the first frame is
  invisible either way.
- **Decision:** direct fix (03 §3.6: no layout jump when data arrives).
  **Timer path:** yes for `BrewSetupScreen` (`feature:brew`, the screen before
  the timer); the timer screen itself is not touched.

### A-13: sheets closed by their own button vanish in one frame (group 3, MEDIUM)

- **Place:** `core/ui/.../StockSheet.kt:67-80` (*Speichern* / *Abbrechen* call
  the host's close, which removes the sheet; used at `TeaDetailScreen.kt:259-268`
  and `BrewSetupScreen.kt:199-205`); `feature/catalog/.../CatalogTeaScreen.kt:103-116`
  (*Aufnehmen*: the VM sets `sheetState = null`); `feature/catalog/.../CatalogScreen.kt:195-215`
  (*Fertig* / *Schließen* of the refresh sheet, *Schließen* of the shared-link
  sheet).
- **Symptom:** a drag or a scrim tap slides the sheet out (Material's hide).
  The sheet's own buttons make it disappear together with the scrim in one
  frame. The Monate, Filter, Descriptor, taste and purchase sheets do it right.
- **Cause:** the composable leaves composition before `sheetState.hide()` runs.
- **Fix:** the established pattern of `TeaDetailPurchaseSheet.kt:78`, shared
  in `core:ui` as `rememberSheetClose(sheetState, onDismissRequest)`:
  ```kotlin
  val close: () -> Unit = {
      scope.launch { if (!reduceMotion) sheetState.hide() }
          .invokeOnCompletion { if (reduceMotion || !sheetState.isVisible) onDismissRequest() }
  }
  ```
  *Speichern* or *Aufnehmen* acts at once, then calls `close`. For the
  VM-driven catalog sheets, keep the last sheet state in the screen
  (`var shownSheet by remember { mutableStateOf(open) }`) and call `close()`
  when the VM's value turns `null`. **Rule 8 unchanged:** the `AlertGate` /
  `!alerting` path still removes a sheet in the alert's first frame without
  `hide()`.
- **Decision:** direct fix. **Timer path:** no (`core:ui`, `feature:catalog`;
  the setup only calls `StockSheet`).

### A-14: the *Gespeichert* sheet's spring starts on the shell's heaviest frames (group 3, LOW)

- **Place:** `feature/journal/.../SavedSheet.kt:170-205` (`visible` only when
  `content?.sessionId == id`), `:253-279` (four sequential reads in
  `produceState`).
- **Symptom (feel-check):** after *Sitzung beenden* the timer pops (A-11's
  whole-shell recomposition) and the sheet's `slideInVertically(sheet) +
  fadeIn(fade)` starts whenever the four reads finish. If that is within the
  first frames, the spring's first steps drop and the sheet seems to jump in
  part-way.
- **Cause:** the enter starts on data arrival, not on a calm frame. The reads
  run one after another.
- **Fix:** run the four reads in parallel (`coroutineScope { async … }`), and
  start `visible` no earlier than the frame after the host's first draw
  (`withFrameNanos {}` once before setting the content). Only if #285 or the rc
  check shows it.
- **Decision:** direct fix after a feel-check. **Timer path:** no.

### A-15: timer exit shows an empty frame before the pop (group 4, HIGH)

- **Place:** `feature/brew/.../timer/TimerRoute.kt:66-81`. When the shown slot
  turns Idle (*Sitzung beenden*, *Verwerfen*, the quick timer's end), `shown ==
  null`, the route composes nothing, and `LaunchedEffect(Unit) {
  currentOnClose() }` pops only after that frame.
- **Symptom:** dark timer → at least one frame of window background (light washi
  in the light theme, a flash) → the shell appears at once (`popEnter = None`).
  The 200 ms `exitFade` then fades an empty, invisible route. The designed
  exit is not seen.
- **Cause:** the close follows the state with an effect, which runs after the
  frame that already has no content. The route has no background of its own
  (A-05).
- **Fix:** (1) the Steeping background under the route, as in A-05, so the pop
  fades a dark surface over the shell (the designed `exitFade`). (2) Keep the
  last shown screen, inert, until the pop: remember the last `Active` in the
  route (`var last by remember { mutableStateOf<TimerUiState.Active?>(null) }`,
  set in a `SideEffect` while `shown != null`). While closing, draw
  `TimerScreen(state = last, onEvent = {}, …)` with no input
  (`Modifier.pointerInput(Unit) {}` to swallow taps), but only if `last` was not
  ALERTING. Never draw a stale alert surface; in that case the background
  alone. **Rule 8:** the pop is never into an alert, and an alert in another
  slot is shown at once by `lastRinging()`, as today.
- **Decision:** direct fix. **Timer path:** yes (`feature:brew`; the 04 §12
  tests and a T4 review of the timer path).

### A-16: status-bar icons flip at navigation start (group 4, LOW, to the PO)

- **Place:** `app/.../UmamitRoot.kt:537-547` (`SystemBarIcons(systemBarDarkIcons(timerOnTop
  = timerShown, …))` from the back stack); `SystemBarIcons.kt` (D-069).

- **Fix:** options in §4.3.
- **Decision:** to the PO (changes D-069's behaviour). **Timer path:** no
