# Motion review: v0.5.0 new/changed screens (diff origin/main...6af2f857)

Read-only review against the project's own motion rules, as the PO chose on 2026-11-09: `docs/specs/03-ux-ui.md`
§3.6 (tokens in `UmamiMotion`, `core/designsystem/.../motion/Motion.kt`), D-041 (calm, ritual-like style;
functional motion only) and D-055 (reduce motion = animator scale 0, every animation ends on its first frame). The
`/review-animations` skill was not used. Scope: `feature/**`, `core/designsystem/**`, `core/ui/**`, `app`. No timer
engine or controller code is touched or proposed (rule 8). Every duration below is an existing `UmamiTheme.motion`
token, so reduce motion is handled by the token (`calm()`/`springOrSnap()` return `snap()`).

Totals: must 0, should 3, nit 3. Section 2 lists what should NOT animate.

**Fixed in the v0.5.0 review fix round (2026-11-09; D-108's build notes):** all six findings, as proposed. S1:
both reorder forms take 8 + 48 dp. S2 and S3: the reveal runs only on a real kind change (`revealedKind`, saved),
reads the spans a frame later and uses `UmamiTheme.motion.standard()` (`snap()` at the first show and under reduce
motion); test `theChipRowKeepsTheUsersOwnScrollWhenItComesBackIntoTheList`. N1: a kind change with the chip row off
screen scrolls the list to it at once. N2: no refreshing row while the shown kind's pending hint is there (03
SCR-19). N3: the *Warnung* switch shows the tap at once (test in `TeaDetailScreenTest`). Section 2 stands.

Overall: v0.5.0 adds one new piece of motion code, the catalog kind row's scroll to the selected chip (#206).
Everything else is a state swap on Material components (dialogs, switches, chips) or a layout change. The risk is
in two places: the new reveal scroll, which uses an untokened spring and also runs when nobody asked for it, and
VORRAT, where the new controls sit right below a control whose height changes when they are used.

## 1. Findings

### S1. should: VORRAT's reorder control changes height right above *Warnung* and *Knapp ab*, so the control in use moves
- `feature/collection/.../detail/TeaDetailSections.kt:202-224` (reorder `if`/`else`) with
  `TeaDetailStockWarning.kt:51-75` (`WarningRow`) and `:80-117` (`ThresholdField`); `prominent` at
  `TeaDetailViewModel.kt:333`.
- Problem: `prominent = tea.lowStockWarning && … && level != AVAILABLE`. A tap on *Warnung* and every valid
  keystroke in *Knapp ab* („5" → „50") can flip it. The prominent branch is `Spacer(Small)` plus a 48 dp
  `PillButton`, which comes to 56 dp. The text branch is a `TextButton`, 48 dp with the minimum touch size. So the
  switch row the user just tapped, or the field holding the caret, shifts 8 dp in one frame, below a button that
  changes shape. The spec places the warning after the reorder link (03, "Stock warning"), so the order stays and
  the slot must stop changing height.
- Fix (layout-stable, no animation): give both branches the same box. Move the spacer out of the `if`, so it is
  `Spacer(Modifier.height(UmamiSpacing.Small))` before both, and give the `TextButton`
  `Modifier.heightIn(min = UmamiSpacing.MinTouchTarget).testTag(TEA_DETAIL_REORDER_TAG)`. Both branches then take
  8 + 48 dp, and only the style swaps. Do not use `animateContentSize`/`AnimatedContent` with a `SizeTransform`: a
  height glide under a focused field still moves the caret, only more slowly. Check the `TeaDetail_*` goldens: the
  text-link case gains up to 8 dp.

### S2. should: the kind row's reveal also runs when the row re-enters the list, and undoes the user's own horizontal scroll
- `feature/catalog/.../CatalogFinding.kt:112-122` (the `LaunchedEffect(filter.kind, filter.marked)`), and the row as a
  `LazyColumn` item at `CatalogScreen.kt:352`.
- Problem: the effect is keyed only by kind and *Gemerkt*. The chip row is a lazy item, so when the list is scrolled
  far enough the row leaves composition, and on the way back the effect starts again. `rememberScrollState` brings
  back the user's horizontal position, but if they had scrolled the row to „Bio" or „Im Besitz", so that the
  selected kind was out of view, the row now slides back to the kind. That is motion the user did not cause, in a
  row they had just placed. A second, smaller issue: the effect reads `kindChips` from the previous layout at
  once. When a kind change also changes the *Filter* chip's label width („Filter (2)" → „Filter", because
  `keepingFlavoursOf` drops notes), every kind chip moves, and the span it reads is stale by that width.
- Fix: remember which kind was last revealed, and reveal only on a real change:
  ```kotlin
  val motion = UmamiTheme.motion
  // The kind last brought into view; saved, so a row that scrolls back into the list keeps the user's position.
  var revealedKind by rememberSaveable { mutableStateOf<String?>(null) }
  LaunchedEffect(filter.kind, filter.marked) {
      if (filter.marked) {
          revealedKind = null // the row is rebuilt when Gemerkt ends: reveal again then
          return@LaunchedEffect
      }
      if (revealedKind == filter.kind.key) return@LaunchedEffect
      val instant = revealedKind == null // first show, or the row just rebuilt after Gemerkt: no travel
      withFrameNanos { } // read this frame's spans, after a Filter label that changed with the kind
      val chip = snapshotFlow { kindChips[filter.kind] }.filterNotNull().first()
      scroll.reveal(chip, side, if (instant) snap() else motion.standard())
      revealedKind = filter.kind.key
  }
  ```
  `reveal` then takes `spec: AnimationSpec<Float>` instead of `animate: Boolean` (S3). Remove
  `val reduceMotion = UmamiTheme.reduceMotion` (`:116`). Keep the #206 tests: a tap and *Alle zeigen* still
  reveal with motion, and leaving *Gemerkt* reveals at once.

### S3. should: the reveal uses Compose's default spring, not a motion token
- `feature/catalog/.../CatalogFinding.kt:193` (`animateScrollTo(target)`), `:116`/`:120` (hand-made reduce-motion
  branch).
- Problem: `ScrollState.animateScrollTo` defaults to `SpringSpec()`, which is critically damped at
  `StiffnessMedium` (1500), a response of about 0.16 s. That is twice as fast as anything else that changes state in
  the app, and outside §3.6's table. The hand-made `animate = !reduceMotion` repeats what the tokens already do.
- Fix: `if (target != value) animateScrollTo(target, spec)`, with `spec = UmamiTheme.motion.standard()`
  (300 ms `CalmEaseOut`, "state and content transitions"; `snap()` under reduce motion). The tween does not block
  the user: a finger on the row cancels it through the scroll mutex. Do not use `sheet()` here. Its physics would
  fit, but the token is reserved for own sheets.

### N1. nit: *Alle zeigen* into another kind keeps the old list's index, so the new kind opens mid-list and the chip row is off screen
- `feature/catalog/.../CatalogScreen.kt:374-384` (the `hidden` row, `showAll`) and `:331` (`listState`).
- Problem: *Alle zeigen* sits at the end of the list. When it switches the kind, the first visible tea row's key no
  longer exists, so `LazyListState` keeps the index, and the user lands somewhere in the middle or at the end of an
  unrelated list. The chip row that S2/S3 would reveal is off screen, so the feedback for the kind change never
  shows.
- Fix (instant, no travel through the old content): bring the chip row back into view when the kind changes and the
  row is not on screen:
  ```kotlin
  var listedKind by rememberSaveable { mutableStateOf(filter.kind.key) }
  LaunchedEffect(filter.kind) {
      if (filter.kind.key == listedKind) return@LaunchedEffect
      listedKind = filter.kind.key
      if (listState.layoutInfo.visibleItemsInfo.none { it.key == "chips" }) {
          // header, refreshing?, guides?, search, chips
          listState.scrollToItem(1 + listOf(state.isRefreshing, state.guideCount > 0).count { it } + 1)
      }
  }
  ```
  A kind change from a chip (row visible) moves nothing. Use `scrollToItem`, not `animateScrollToItem`: the content
  was replaced, so animated travel would only scroll through rows of the new kind that mean nothing yet.

### N2. nit: *Jetzt laden* in a pending hint pushes the hint down under the finger
- `feature/catalog/.../CatalogScreen.kt:349` (`refreshing` item), `:357-358` (`kind_pending`), `:460-467`
  (`PendingKindRow`).
- Problem: a tap on *Jetzt laden* starts the refresh. `RefreshingRow` is then inserted at index 1, above search and
  chips, and everything below it drops by that row's height in one frame. The hint the user just tapped moves away,
  and its button turns into *Fortschritt anzeigen*, which does the same as the inserted row. v0.5.0 brings this
  from the *Kräutertee* view to seven kinds' views (D-108).
- Fix (no animation): while the shown kind's hint is there, leave out the duplicate row:
  `if (state.isRefreshing && filter.kind !in state.pendingKinds) item(key = "refreshing") { … }`. The hint's own
  action is the progress link. This changes SCR-19's refresh row, so update its line in 03 in the same PR. Do not
  use `Modifier.animateItem` instead: the tea rows below would also need placement animation, and that is rejected
  for the list (section 2).

### N3. nit: the *Warnung* switch moves only after the Room round trip
- `feature/collection/.../detail/TeaDetailStockWarning.kt:51-75`; `TeaDetailViewModel.kt:170`.
- Problem: `Switch(checked = tea.stockWarning)` is driven by the stored value. The thumb's own Material animation
  starts only once the write has gone through Room's invalidation and the detail flow, a few frames after the tap.
  The ripple answers at once, but the thing being changed answers late.
- Fix: show the tap at once and let the stored value correct it:
  `var checked by remember(on) { mutableStateOf(on) }`, `toggleable(value = checked, …, onValueChange = { checked = it; onWarning(it) })`,
  `Switch(checked = checked, onCheckedChange = null)`. Material keeps its own thumb motion, with no custom spec.
  The reorder highlight (S1) still follows the stored value.

## 2. Rejected: these must NOT animate

| Where | Why not |
|---|---|
| Active brew bar: one bar ↔ two halves, a second brew taking a half (`ActiveBrewBar.kt:123-133`) | As decided in D-098, the second half comes and goes without motion of its own. The swap happens almost only while the bar is not on screen (starting opens the timer route above the shell; ending happens on timer routes). A slide or width animation of a half would sit next to an alerting half that must snap. |
| Held half „wartet"/„fertig" → ringing matcha (`ActiveBrewBar.kt:233-285`) | Entering ALERTING is `alertEnter` (snap, rule 8). The held label is a state word, not a pulse or fade. The bar's `enter = None` when either half alerts is right. |
| Halves never slide or swap sides | Their order is the slot order (D-108). If a reshuffle is ever seen on the device, fix it in the order, never with motion. |
| Timer route switching to the ringing brew and back after *Abgegossen* (`TimerRoute.kt:139-149`) | A `Crossfade` keyed by slot would fade into ALERTING (forbidden) and soften the alert's onset. Leaving the alert stays a snap (§3.6 `emphasized` note). |
| Slim row for the second brew (`TimerOtherRow.kt:74-140`) | Hidden on the alert surface with its space kept (rule 8). The full/short detail swap and the ticking countdown are text, and tabular figures keep the width steady. |
| „Welchen Timer beenden?" (`ChooseTimerToEndDialog.kt`) | Material `AlertDialog` default, like `FinishActiveSessionDialog`. No stagger or highlight of the timer buttons. The question closes at once (`pending = null`) before the start, and alert-gated removal stays frame-exact. |
| Start: *Aufguss starten* below the active card, the card switching to the second brew (`HomeScreen.kt` `BrewCards`) | The state changes while Start is not on screen (a start navigates to the timer). When the user returns, the route transition is the change. Both cards keep their `press` scale; no entry stagger. |
| Kind chip selection colour, the „Pur" chip leaving/arriving, the header count („186 Schwarztees") | Direct result of the tap; the reveal (S2/S3) is the one piece of motion. |
| Catalog list content on a kind change, pending hint row appearing/leaving | Whole content replaced. `animateItem` on tea rows would make hundreds of rows glide on every filter. |
| Filter sheet: taste note chips, scale rows „Egal · ab 1 … ab 5", groups that differ per kind | Selection is instant feedback. The note and scale options come from the kind's range (`CatalogListing.tasteNotes` KDoc), so they do not reorder under the finger. No `animateContentSize` on the sheet. |
| *Knapp ab* hint ↔ error text, stock line „· knapp" | They change per keystroke; never animate keyboard-rate changes. |
| Reorder text link ↔ filled pill (after S1, same height) | A state label of *Knapp*; instant. |
| Settings: *Uhrzeit* row appearing or leaving when the interval goes to or from *Aus* | It happens behind the dialog's scrim; once the dialog closes, the page is simply in its new state. Radio buttons keep Material's motion. |

## 3. Checked and fine
- No motion token, easing or `UmamiMotion` code changed; no new `tween`/`keyframes` in the diff apart from the
  reveal (S3).
- Alert gate: the new dialog and the filter sheet are composed only while no alert plays (`AlertGated` or
  `!alerting`), and they are removed in an alert's first frame without an exit animation.
- `ActiveBrewBar` still grows from its bottom edge with `activeBrewBar()` + `fade()`/`exitFade()`, and snaps in
  when it arrives alerting.
- Seal and stock on the timer route are per-slot `StateFlow`s held in the view model (`TimerViewModel.kt:85-87`),
  so switching between two brews' routes shows them at once, with no pop-in.
- The filter sheet keeps `rememberCatalogSheetState` (reduce motion: starts `Expanded`, no slide). Out of scope:
  *Fertig* removes it from composition without an exit (the v0.4.1 S1 pattern, unchanged here).
- Hover and pointer gating: not applicable (touch only).
