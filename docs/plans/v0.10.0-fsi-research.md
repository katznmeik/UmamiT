## 1. What resets the grant (the mechanism)

1. **The permission is an app-op permission.** `USE_FULL_SCREEN_INTENT` is
   declared `android:protectionLevel="normal|appop"`
   [fetched: `M`core/res/AndroidManifest.xml; also seen on `main`]. Its app-op
   `OP_USE_FULL_SCREEN_INTENT` has no explicit default mode, so its default is
   `MODE_DEFAULT` [fetched: `M`core/java/android/app/AppOpsManager.java,
   `M`core/java/android/app/AppOpInfo.java, read on `main`]. With
   `MODE_DEFAULT` the check falls back to the normal permission, which is
   granted at install. With `MODE_ERRORED`/`MODE_IGNORED` it is hard-denied
   [fetched: `checkAppOpPermission` in
   `M`services/core/java/com/android/server/pm/permission/PermissionManagerService.java,
   read on `main`]. The setting „Vollbild-Benachrichtigungen" is this app-op
   (AOSP Settings: `OP_USE_FULL_SCREEN_INTENT`, `setModeByUid = true`)
   [fetched: raw.githubusercontent.com/aosp-mirror/platform_packages_apps_Settings/main/src/com/android/settings/spa/app/specialaccess/UseFullScreenIntent.kt].
2. **The system package installer denies FSI on every sideload.** The platform
   package installer app, which opens an APK from a browser download or a file
   manager, builds its session with:
   ```kotlin
   // Disable full screen intent usage by for sideloads.
   params.setPermissionState(
       Manifest.permission.USE_FULL_SCREEN_INTENT, SessionParams.PERMISSION_STATE_DENIED
   )
   ```
   This line has no condition on new install or update, target SDK, category or
   role. It is in both installer flows:
   - v2: [fetched: `M`packages/PackageInstaller/src/com/android/packageinstaller/v2/model/InstallRepository.kt,
     also on `main` and `android16-qpr1-release`];
   - v1: [fetched: `M`packages/PackageInstaller/src/com/android/packageinstaller/InstallStaging.java,
     also on `android14-release`, `android15-release` and `android16-qpr1-release`].

   The public API allows any installer to set this one permission:
   „Holders without the permission are allowed to change the following special
   permissions: On platform UPSIDE_DOWN_CAKE: USE_FULL_SCREEN_INTENT"
   [fetched: https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setPermissionState(java.lang.String,%20int)].
3. **From Android 15 on, the platform applies that DENIED on every install,
   updates included, and does not check the user's own choice.**
   - `PermissionManager.USE_ACCESS_CHECKING_SERVICE = SdkLevel.isAtLeastV()`,
     so from Android 15 the permission service is the new
     `services/permission/.../PermissionService.kt`, not the old
     `PermissionManagerServiceImpl` [fetched: `M`core/java/android/permission/PermissionManager.java;
     `M`services/core/java/com/android/server/pm/permission/PermissionManagerService.java].
   - Its `onPackageInstalled` calls `setRequestedPermissionStates(...,
     params.permissionStates)`. For a permission in
     `INSTALLER_CHANGEABLE_APP_OP_PERMISSIONS` (which holds only
     `USE_FULL_SCREEN_INTENT`), that calls `setAppOpPermissionGranted`, which
     sets the app-op to `MODE_ERRORED` for DENIED. There is **no
     `FLAG_PERMISSION_USER_SET` check** on this path
     [fetched: `M`services/permission/java/com/android/server/permission/access/permission/PermissionService.kt,
     same code on `main`;
     `M`services/core/java/com/android/server/pm/PackageInstallerService.java].
   - `InstallPackageHelper.updateSettingsInternalLI` passes the session's
     permission states to `onPackageInstalled`. That method handles fresh
     installs and replacements alike: its code preserves install reasons
     „When replacing an existing package"
     [fetched: `M`services/core/java/com/android/server/pm/InstallPackageHelper.java].
     That this runs on every update is an inference from reading the code. It
     was not traced at run time.
   - By contrast, the **old** implementation (Android 14) skips the installer's
     state when the user has set it (`if ((flags & FLAG_PERMISSION_USER_SET) != 0) continue;`)
     [fetched: raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/android14-release/services/core/java/com/android/server/pm/permission/PermissionManagerServiceImpl.java].
     AOSP Settings sets `USER_SET` when the toggle is flipped
     [fetched: `M`… `android16-qpr1-release`
     packages/SettingsLib/SpaPrivileged/src/com/android/settingslib/spaprivileged/model/app/AppOpsController.kt].
     So on Android 14 a grant set by the user would probably have survived an
     update. On Android 15+ AOSP it does not.
4. **Nothing else resets it on update.** AppOpsService only refreshes
   attributions on `ACTION_PACKAGE_REPLACED`. It resets ops only on a real
   removal (not when `EXTRA_REPLACING` is set)
   [fetched: `main` services/core/java/com/android/server/appop/AppOpsService.java].
   This matches D-134 Q4: *Alle Daten löschen* (clearing the app's data) kept
   the grant.

**Conclusion (AOSP 15/16):** the user's grant is lost because the system
package installer marks every sideloaded install and update with FSI = DENIED,
and Android 15+ applies that over the user's earlier choice. It is not caused
by the app, its target SDK or its alarm setup. **Whether Android 17 / One UI 9
behaves the same is [unverified]:** no Android 17 source was available.
Samsung may ship its own build of the installer and Settings. The PO's report
(lost after every update) fits the AOSP 15/16 code exactly.

## 2. Does the install method matter?

| Way of installing | What it sends for FSI | Expected effect on the grant |
|---|---|---|
| Browser download → tap → system package installer (today's way) | DENIED [fetched, §1.2] | Lost (§1.3) |
| File manager (*Eigene Dateien*) → system package installer | DENIED; it is the same installer app [fetched, §1.2] | Lost |
| `adb install -r` (`pm install`) | No FSI state; `PackageManagerShellCommand` never calls `setPermissionState` [fetched: `M`services/core/java/com/android/server/pm/PackageManagerShellCommand.java] | **Kept** (inference: an absent state is skipped in `setRequestedPermissionStates`) |
| `adb install -r -g` | `INSTALL_GRANT_ALL_REQUESTED_PERMISSIONS` turns every requested permission into GRANTED, FSI included [fetched: `M`…/InstallPackageHelper.java] | Granted, but so is every other requested permission (e.g. notifications). Not recommended |
| A third-party installer app using the session API | Whatever that app sets; DEFAULT if it does not call `setPermissionState` | Kept if it does not set DENIED. Which apps do so is **[unverified]** |
| Play Store | Not used. Play revokes FSI for apps that are not alarm or calling apps [fetched: https://developer.android.com/about/versions/14/behavior-changes-14] | n/a |

**Update ownership / installer of record:** `setRequestUpdateOwnership` only
decides whether another installer needs the user's confirmation. It can be
enabled only on the first install, and only by an installer holding
`ENFORCE_UPDATE_OWNERSHIP` [fetched: SessionParams reference]. Nothing in the
code read ties the FSI state to the installer of record. The denial comes from
what the installing session sends. **[unverified]:** whether One UI 9
substitutes a Samsung installer for the AOSP/Google one.

## 3. Target SDK, alarm category, `setAlarmClock()`, alarm/calling app

None of these changes what the system installer sends or how Android 15+
applies it:

- the DENIED line has no condition (§1.2);
- `setRequestedPermissionStates` checks no target SDK, role or notification
  category (§1.3);
- the notification service only treats `targetSdkVersion < Q` specially (always
  allowed) [fetched: `main` services/core/java/com/android/server/notification/NotificationManagerService.java,
  `checkUseFullScreenIntentPermission`]. That cannot apply here (min SDK 35).

The „alarm or calling apps only" rule is a **Play Store** policy for apps
installed from Play [fetched: Android 14 behaviour changes]. The policy page
itself (support.google.com) could not be reached, so its exact wording is
[unverified]. `CATEGORY_ALARM` (already used) and `setAlarmClock()` (the timer
uses `setExactAndAllowWhileIdle`) are not part of this path. Becoming the
default dialer (a calling role) is out of scope and would not change the
installer either. Whether a role holder is exempt is [unverified/recall].

Neither Android 17 behaviour-change page mentions full-screen intents, the
package installer or app-op defaults
[fetched: https://developer.android.com/about/versions/17/behavior-changes-all,
https://developer.android.com/about/versions/17/behavior-changes-17; no mention].

## 4. Legitimate ways to keep the grant (no bypass)

The user's grant is respected only if the update is **not** installed by a
session that sends DENIED. Ways that respect the user's own choice:

- **(L1) Update over adb (`adb install -r`)** from a computer: nothing changes
  in the app. It needs a PC with adb and USB or wireless debugging on the
  phone. *Not* `-g` (§2).
- **(L2) A third-party installer app the PO chooses** that installs APKs
  through the session API without setting FSI. Some such apps can also track
  GitHub Releases. That tracking would be the installer app's own network use,
  not UmamiT's. Which apps send FSI = DEFAULT is [unverified] and must be
  probed.
- **(L3) An in-app „Update aus Datei installieren"**: UmamiT installs an APK
  that the user picks with the file picker, through `PackageInstaller` sessions
  with FSI left at `PERMISSION_STATE_DEFAULT` (never GRANTED). The user still
  confirms the install dialog.
  - Costs: a new permission `REQUEST_INSTALL_PACKAGES`, which changes the
    manifest permission check (06 §5.7); a one-time grant of „Unbekannte Apps
    installieren" for UmamiT; new UI, strings and specs.
  - A **download from GitHub inside the app is excluded** by CLAUDE.md rule 7
    (network only to tee-kontor-kiel.de).
  - Only updates would keep the grant; a fresh install still starts denied.

Not legitimate or not useful:

- sending `PERMISSION_STATE_GRANTED` from an in-app installer, since it would
  grant FSI without the user's toggle;
- `adb install -g`, since it grants every requested permission;
- declaring the app an alarm or calling app, a category trick or
  `setAlarmClock()`, since none of them changes this path (§3).

## 5. Probe steps for the PO (with the v0.10.0 rcs, no probe build)

The rcs can answer this, so no probe build is needed. In every step, record
three things **before and after**:

- (a) the switch at *Einstellungen › Apps › UmamiT › Vollbild-Benachrichtigungen*
  (the menu path on One UI 9 is [unverified]; the app's *Beheben* link opens
  the same page);
- (b) whether the TMR-31 banner „Der Timer ist eventuell unzuverlässig" is
  shown on Home;
- (c) whether the SCR-34 sheet appears on the first open. It appears only for
  a new versionCode.

1. **The usual way.** Before: the current build with the switch **on** and no
   banner. Download `v0.10.0-rc.1` in the browser, tap it and install over the
   old build. Expected per AOSP 15/16: switch off, banner shown, sheet shown.
   Use *Erlauben* in the sheet and check that the switch is on again.
2. **Same file again, from the file manager.** With the switch on, open the
   same rc.1 APK in *Eigene Dateien* and install it over itself (same
   versionCode; the installer offers it as an update). Expected: switch off,
   banner shown, no sheet (same versionCode). This shows that the file manager
   way behaves the same and that any reinstall resets the grant, not only a
   version change.
3. **Next rc, granted by hand.** Turn the switch on in Settings directly, not
   through the sheet, then install `v0.10.0-rc.2` the usual way. Expected: off
   again. This rules out a difference between granting through the sheet and
   granting in Settings.
4. **Optional, only if a computer with adb is at hand.** With the switch on:
   ```
   adb shell appops get com.umamit.app USE_FULL_SCREEN_INTENT
   adb install -r UmamiT-v0.10.0-rc.N.apk
   adb shell appops get com.umamit.app USE_FULL_SCREEN_INTENT
   ```
   Expected: `allow` before, still `allow` after, and the switch still on.
   After a step-1 install the same command shows the mode as denied or
   `errored`. This confirms L1 and the mechanism on One UI 9.
5. **Optional, only if the PO picks option C below:** one update through the
   chosen third-party installer, recorded the same way.

How to read the results:

- **Steps 1–3 off and step 4 kept:** the mechanism in §1 holds on One UI 9.
- **Step 4 also lost:** One UI 9 or Android 17 resets the grant in another way
  [unverified], and only the SCR-34 sheet helps.
- **Step 1 kept:** the reset is not on every update. The PO reports how the
  failing updates were installed.

## 6. Recommendation, as options for the PO

The research does not change the SCR-34 sheet (D-136 item 13). Options B–D
would be **D-136 amendments**, decided by the PO after the probe:

- **A — Keep the SCR-34 sheet only (as decided).** No more work. The grant is
  lost on each update, and the sheet brings it back with one tap.
  *Claude's suggestion for v0.10.0.*
- **B — A + updates over adb when a computer is at hand.** No app change. One
  short how-to line in the release notes or docs. Step 4 confirms it first.
- **C — A + a third-party installer app chosen by the PO.** No app change. It
  needs a probe (step 5), and the choice of app is the PO's.
- **D — A + in-app „Update aus Datei installieren" (L3), in a later release.**
  It needs a new permission (06 §5.7), new specs, UI, strings and a T3+ ticket.
  It must leave FSI at DEFAULT and never download, by rule 7. Not suggested for
  v0.10.0.
