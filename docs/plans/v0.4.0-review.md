## Report 1 — Standards (T3)

### v0.4.0 standards review (dd5336c...HEAD)

## Hard violations

1. **Rule 8: three editors have menus and dialogs with no alert gate** (CLAUDE.md rule 8; 03 §SCR-03: "Like every menu it never covers an alert: an alert removes it in its first frame"). The root only pops routes *above* the shell (`UmamitRoot.kt:650-655`). Tab-internal routes stay under a new alert. `TeaEditorHost`, `RecipeEditorHost` and `VesselEditorHost` take no `alertKey`, so these stay over the alert:
   - `TeaEditorScreen.kt:145` (discard dialog), `TeaEditorInputs.kt:110` (`DatePickerDialog`), `:197` and `TeaEditorFields.kt:307` (`ExposedDropdownMenu`);
   - `RecipeEditorScreen.kt:138-139,225,254`; `RecipeStepsEditor.kt:162` (`DurationPicker`), `:333,:387`;
   - `VesselEditorScreen.kt:144,222,412`. The settings-tab instance (`UmamitApp.kt:743`) is affected; the root instance is popped.
2. **MyTeas chips gate on a Boolean** (`MyTeasParts.kt:172,178,213,215`: `expanded = open && !alerting`). This differs from rule 8 as documented:
   - `open` stays true, so the menu comes back after the alert instead of closing for good (D-077 pattern);
   - setting `expanded=false` runs Material's exit animation over the alert's first frames. `TeaDetailScreen.kt:264-266` documents and avoids exactly this.
3. **Stale KDoc, confirmed.** `SessionRepositories.kt:52` says "deletes the never-started rows". The implementation keeps them (`RoomSessionRepositories.kt:73-78`, Q-19/D-100), and so does the fake.
4. **Commit `d88f470`** has no requirement ID (CLAUDE.md Conventions).

## Suspected SCR-21 back button: real (pre-existing code, reached by a moved route in this diff)
- `CatalogTeaScreen.kt:212` (and `GuideScreens.kt:290`) draw a `Surface` with `surfaceContainerHigh.copy(alpha=…)` and no `contentColor`.
- `contentColorFor` finds no scheme match and falls back to `LocalContentColor`. `UmamiTheme` (`Theme.kt:43`) provides none, so it is `Color.Black`.
- Inside the tab, `NavigationSuiteScaffold`'s Surface supplies `onBackground`, so it is fine there.
- `SetupCatalogTeaRoute` (`UmamitRoot.kt:387`) is a root route outside the scaffold, so the arrow draws black on a dark surface in dark theme.
- `TeaDetailScreen.kt:328-336` (`OverPhoto`) already fixes this explicitly. Apply the same fix and share one component.

## Architecture (judgement)
- No feature→feature imports or Gradle deps; no main-thread DB or runBlocking; no mocks; fixtures are synthetic. OK.
- Form parsing is logic in feature modules ("pure Kotlin modules for logic"). `TeaEditorForm.kt:127-158` copies `AddSheetState.kt:150-201` (catalog) but drops the grouped forms, so "1.234,50" is accepted in the add sheet and rejected in the tea editor. Move it to `core:domain`.
- `alerting: Boolean` (MyTeas, CollectionTab) vs `alertKey: String?` (TeaDetail, Settings) for the same concern is Primitive Obsession and inconsistent.

## Report 3 — Timer-adjacent (T4)

### T4 review: v0.4.0, timer-adjacent parts (dd5336c...HEAD)

## Blockers
None. Checked and clean:
- **#152 (`completeSession`):** the only change is the removed DELETE, so it does no new work inside the transition transaction. `planned_step_count` is still read before, `ended_at` comes only from rows that have one, and the cost is unchanged.
- **Consumers:** journal counts, Home recents, `brewAgainStart`, `savedSummary`, `endOrphans` and active-brew restore read only ended or in-progress rows. Never-started rows are always a suffix. No backup or stats code exists yet.
- **Routes:** every new setup entry (`openSetupWith`, `openSetupFromSession`, Tee ansehen, Neues Gefäß) checks for a playing alert. Every new full-screen route counts as `isAboveShellAndTimer`, so it gives way to a new alert.
- **Archive and delete refusal:** every caller goes through `TeaArchive`/`VesselArchive`. The `active_brew` check and the write share one transaction. The quick slot has no session, so it never hides the brew's tea.

## Should-fix
1. **Saving into the session's existing recipe stores the wrong temperatures.** `SetupEdits.kt:70`, `BrewSetupViewModel.kt:440-451`.
   - **Cause:** `initialEdits` puts the session's `baseTempC`/`method` on top of the recipe. `appliedTo` then stores each step's temperature relative to the setup's base but keeps the recipe's own base and method.
   - **Scenario:** the test's own fixture (`BrewSetupFromSessionTest:66,113`) has recipe base 70 °C and session base 65 °C. *Im Rezept speichern* stores the 75 s infusion with `tempC` null, so it brews at 70 °C next time although the setup showed 65 °C. `differsFrom` stays true, so the save button never flips to „Im Rezept gespeichert".
   - **Breaks:** BRW-02 ("every value of this session into the recipe") and BRW-06 ("the recipe is changed only by *Im Rezept speichern*").
   - **Why now:** the recipe editor (#156) can change base temperature and method, so this mismatch is now normal.
   - **Fix:** compare against `recipe.baseTempC`, or write `baseTempC` and `method` too. The test should assert the stored temperatures.
2. **A double tap on „Ohne Rezept" › *Im Rezept speichern* creates duplicate recipes.** `BrewSetupViewModel.kt:168-179`.
   - **Cause:** the button stays tappable until `saveRecipe` returns (`BrewSetupParts.kt:163-183` expects double taps). Each tap launches its own coroutine that re-reads `source` from the database and still sees `recipeId == null`.
   - **Result:** two recipes named „Kräftig" with different UUIDs. The DAO caps the count at 10 but doesn't catch the duplicate.
   - **Breaks:** D-100 #159 note ("saves a new … recipe").
   - **Fix:** reserve the new id synchronously (`setEdits(recipeId = id)` before launching, kept in SavedState) so a second save upserts the same row. A Mutex would also do.
3. **„Ohne Rezept" loses the session's Vorwarnung base B.** `BrewSetupViewModel.kt:335,376`.
   - **Cause:** with no recipe, the setup uses the global B. The session stores its own B in `brew_session.pre_alert_seconds`, and `brewAgainStart` uses it (`BrewStarter.kt:105`).
   - **Scenario:** the deleted recipe had Vorwarnung *Aus* and every step was *Automatisch*. The re-brew now pre-alerts at the global 10 s on every step, and the new recipe saves B = null.
   - **Breaks:** BRW-06 ("as brewed … with its Vorwarnung"). The #159 build note chose the global B, but that is Claude's detail, not the PO's.
   - **Fix:** use `session.preAlertSeconds` for Ohne Rezept and its new recipe, or get the PO to confirm the current behaviour.
4. **The accuracy harness can measure the quick timer's pre-alert with the screen on.** `AccuracyRunTest.kt:268,565-568`.
   - **Cause:** in the `alongside` variant, the quick timer's pre-alert comes 15 s after its start. The screen-off wait grew from 5 s to up to 10 s plus a 1 s settle.
   - **Scenario:** on a slow emulator (the very case #151 fixes) the quick pre-alert can sound before the screen goes off. It still counts toward p95/max, and a screen-on cue is the easy case (no Doze). The brew side has this guard (`:289`); the quick side has none.
   - **Breaks:** 04 §12 / TMR-30 ("screen off during every step").
   - **Fix:** add the same check for the quick timer, or assert the screen was off before its scheduled pre-alert.

## Nits
5. **`ProcessDeathTest.kt:653` (`TOGETHER_MS` 1 s → 2 s):** this doesn't hide lateness. `LATE_TOLERANCE_MS` is separate, and a brew alert later than the gap fails loudly. But "due together" may now be two separate wake-ups, so handling both deadlines in one turn is covered only by the JVM tests (TwoTimersTest). Log the actual gap.
6. **`START_TIMEOUT` 30 s:** acceptable. Start latency is not a TMR-30 target; cue times come from the diagnostics log, and the brew's 50 s check still uses `stepStarted`.
7. **`BrewSetupViewModel.kt:122-124`:** `edits.value ==\n null` is a formatter artifact; tidy it.
8. **Recipe deletion during a brew:** a recipe deleted (new in v0.4.0) while its session runs leaves *Brühen anpassen* (BRW-11) falling back to the default recipe (`initialEdits`, `:436`). A later save then writes into the wrong recipe. Consider the E15-style refusal for the active session's recipe too.
